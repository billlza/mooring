# Mooring

Mooring 让少数受信任的大陆用户经运营者在英国的移动网络出口上网。流量路径：

国内 CFM 客户端 → 伦敦 VPS（VLESS+REALITY+Vision / Hysteria2）→ WireGuard 隧道（由出口 Mac 主动拨出）→ 出口 Mac → NETGEAR M7 Pro → 1pMobile（EE 网络）→ 互联网。

出口线路自 2026-10-23 起是 1pMobile 的 Unlimited Data Boost（每 30 天 £25，滚动 30 天用量超过 500 GB 即视为非个人使用；运营者决策 F1）；此前选定的 SMARTY 线路已于 2026-10-17 放弃。移动线路的 IPv4 通常处于运营商 CGNAT 之后（在 SMARTY 上已实测确认），出口 Mac 不能指望接受入站连接，因此由 VPS 面向国内、Mac 主动建立隧道并作为出口。完整设计、威胁模型、取舍与里程碑见 [docs/design.md](docs/design.md)。

## 当前状态

2026-11-14（尚未部署）：M7 的信号历史可以导出成表格，并在 MATLAB 里观测和分析（设计 §15.6 第 13 条）。`mooringctl router history --csv samples` 每次轮询一行（时间、信号 RSRP/RSSI、质量 RSRQ/SINR、频段、辅载波数、4G/5G、网络代码、会话与运行时长、温度，或轮询失败的原因），`--csv events` 每次变化一行（掉线与恢复、频段或网络变化、重启等）；表头就是格式的版本，日期范围与摘要、`--json` 相同（默认昨天和今天，最多 90 天）。重定向到文件即本机导出；接上管道即推送到运营者自己的另一台机器（`… --csv samples | ssh <机器> 'cat > radio-samples.csv'`）。出口 Mac 只向外发送：不开放任何入站连接，不新增监听，也不提供“从别的机器 ssh 进来拉取”（设计 §18）；接收的机器不能在学校网络上（F15）。`matlab/+mooring` 读取这两张表（表头不符、任何一行不合格式、同一行的两个时间不一致、文件被截断都会报错而不是猜），并提供：`radioHourly`（每小时的轮询数与各读数的中位数）、`radioDegradation`（最近 24 小时对比此前 7 天每天的同一时段，逐项给出 ok / degraded / insufficient_data：比这 7 天的中位数差出阈值、并且超出这些天彼此之间波动的三倍，才算 degraded）、`radioForecast`（按每个钟点在过去 14 天里的中位数外推未来 48 小时，并用历史的最后一段回测自己的误差；历史的趋势只报告，默认不外推，`Trend=true` 才外推）、`plotRadio`（信号、质量、频段、载波、服务与事件的总览图）；不依赖任何工具箱。两条规则都用 2026-11-14 当时 Mac 上的 16 天真实历史看过（不经 MATLAB，脚本只输出计数和比例）：两张表共 19937 行样本、578 行事件，逐行符合读取规则；只按阈值判断时，9 天里有 8 天报退化，多半是 5G 占比平日的起伏；加上波动条件后是 5 天，其中连续 3 天每天带 5G 读数的轮询都不到 30 次；按钟点的预测误差是“和前一天同一钟点一样”的 67 % 到 100 %；外推趋势对 NR SINR 更准（80 % 到 82 %），却让 NR RSRP 的预测比“和前一天一样”还差（113 % 到 122 %），其余读数相差不超过 4 个百分点，所以趋势留作选项、默认不外推。16 天只够看一眼，不算校准：阈值仍只是起点，由运营者自己调。出口 Mac 上没有 MATLAB，MATLAB 测试只在托管 CI 上运行（`.github/workflows/matlab.yml`）。用法见 [docs/runbooks/radio-analysis.md](docs/runbooks/radio-analysis.md)。装上带这项改动的构建之后才有 `--csv`。

2026-11-12（2026-11-13 部署）：每晚的执行任务落地（设计 §13.6）。App 在注册守护进程时一并注册第二个 LaunchAgent `com.bill.mooring.apply`，每小时第 20 分运行 `mooringctl apply --pending`，只在 UTC 19:15–19:45（北京时间凌晨 3:15–3:45）之间真正执行，睡眠后迟到、落在窗口外的触发什么都不做；`mooringctl apply --now` 立即执行。每次依次：暂停到期和用完配额（自己的、自动的或付费月份的）的用户，时间记为本次运行的时刻；恢复原因已消失的暂停（上一个计费周期的超额暂停；本周期的超额暂停在买了够用的流量包、付费月份或调高配额后，下一次运行即恢复，用量数据落后时则等到下一个周期；以及付费后不再到期的到期暂停），受活跃人数上限约束，最早暂停的先恢复，被上限挡住的只报告；删除作废满 13 个月的用户；最后对配置代数落后的节点做 apply，节点连不上只报告，不影响前面的暂停和恢复。出现时钟回拨（`QuotaSuspensionAfterNow`）时整步不执行，只报告。运营者或滥用审查的暂停从不自动恢复。状态版本升为 3：`Revoked{since}` 记录作废时间；`mooringctl user forget <uid>` 立即删除已作废的用户，守护进程随后删除其用量记录和付款账本中的订单，付款账本不再永久保留已删除用户的订单。执行任务的日志 `~/Library/Logs/Mooring/apply.log` 只记数量、不写用户。全额退款（运营者 2026-11-12 决定）从门户记下退款的时刻起收回这张订单给的、用户还没用到的时间和流量：服务期从那一刻起不再算（还没开始的整段收回），排在它后面接着续上的服务期整体往前挪；流量包只留下用户在退款那一刻超出其余配额已经用掉的部分：退款先记为“等用量”，流量包照旧全额计算；守护进程采集的用量覆盖到退款时刻之后几分钟（正常在退款后十分钟左右），按 5 分钟分档算出当时的用量：退款后 3 到 8 分钟内的流量、以及分档缺失时分不清的流量，都算作用户已用；退款时还没结束的 REALITY 下载，Xray 要到连接关闭才计数，节点分不清它和退款之后才开始的下载，所以（运营者 2026-11-12 决定）此后各节点新计入的 REALITY 下载流量也都算作退款时已用，直到该节点的 Xray 重启过（改动其配置的 `node apply`，例如每晚任务暂停或恢复该节点上的用户，或自动升级后的重启）或计费周期结束；代价是在那之前，用户最多可以再多用一份与已退流量包等量的 REALITY 下载流量，之后再买的流量包不为它扣量（运营者同日决定不为此设时限：设了时限，超过时限仍未结束的下载又会算在退款之后）；没有再买流量包、也没有调高配额时，用量达到不含该包的配额的用户照样在下一次每晚任务被暂停；从得知的那一刻起只保留这部分；到流量包所在的计费周期结束还没等到用量的，什么都不收回。已经用掉的不追回，同一周期里之后再买的流量包不会替旧包补用量；部分退款什么都不变。付款账本升为第 3 版，第 1、2 版读入时自动升级。退款的日志行只写订单、不写用户，`mooringctl portal payments` 标出还在等用量的退款，以及仍在计入 REALITY 下载的退款和对应的节点。控制台的节点页显示每个待执行的 apply 和已等待的时间。它随 main `8c705c6` 于 2026-11-13 部署：守护进程自 UTC 02:22 起运行这份构建，launchd 自 03:20 起每小时第 20 分启动一次执行任务，写下这句时（UTC 09:22）已启动七次，都在窗口外，以退出码 0 结束、不写日志。第一次落在窗口内的运行是当天 UTC 19:20（北京时间 14 日凌晨 3:20），写下这句时尚未发生；从这一晚起，它在北京时间凌晨自动暂停到期和超额的用户。换新构建后，它的登记不会随守护进程一起修复：须按运行手册第 1、7 节，在等待守护进程退出码 78 的那一分钟里用 `launchctl kickstart` 手动启动它两次，否则它从下一个第 20 分起被 launchd 拒绝、不再运行，而菜单仍显示它已登记（2026-11-13 用一次性测试 App 实测，设计 §5.1；Mooring 自己的任务尚未经历过换构建）。用法见 [docs/runbooks/console.md](docs/runbooks/console.md) 第 7 节。

2026-10-23（M7）：`Mooring.app` 能显示部署后的完整状态（出口、SIM、节点、用户、容量与告警），并由 App 用 `SMAppService` 把守护进程注册为登录项（菜单栏或主窗口工具栏的“守护进程”菜单里的“登录时启动守护进程”/“停止守护进程”），注销或重启后登录即恢复；守护进程不再需要 `--router-interface`，改从 `router pin --interface` 记录的身份文件（第 2 版）读取 M7 接口，并自行写入按 5 MiB 滚动的日志 `~/Library/Logs/Mooring/daemon.log`。

有部署时，守护进程启动 App 包内的电源助手 `mooring-power`：出口启用且接通电源时，它持有 `NetworkClientActive` 与 `PreventUserIdleSystemSleep` 两条断言（`pmset -g assertions` 中名为 “Mooring exit”），使 Mac 不休眠；改用电池时释放断言，出口为 `Degraded`（`OnBattery`）。Mac 仍要休眠时（合盖、手动睡眠），守护进程先停止 `mooring-exit`，再在共 4 秒的预算内请每个节点为排空关闭闸门（每次 SSH 会话到预算用尽即连同拨号进程整组终止），出口保持 `Paused` 直到唤醒，唤醒后重新探测并启动。控制通道的每个连接以一行协议声明开头（`{"control_protocol":2}`）：App 更新后若守护进程仍是旧版本，`mooringctl` 会提示重启守护进程，而不是读不懂回复。

设计第 7 版（2026-10-13）：M1（纯 Rust 核心，4a95ee0）以及其上的控制台基础与第 6 版落实的运营者决策（71af715）均已提交。M2a 在 SMARTY 卡到货前完成了步骤 1–3（记录见 [docs/measurements/M2.md](docs/measurements/M2.md)）：M7 的 JSON 接口为 `GET /api/model.json?internalapi=1`，状态字段需要登录，登录后的文档以明文携带管理员密码、Wi-Fi 密钥与设备和用户标识，M7 时钟不可信。`crates/daemon-core` 据此实现了 MR7450 `model.json` 的白名单解析器与脱敏器（共用一张白名单表），路由器状态类型按设备实际上报的字段重塑。`crates/macsys` 读取内核路由表与邻居表；`mooringctl` 首批路由器命令 `router pin | set-password | status | capture`（只读访问 M7，仅 macOS）已实现并在本机回环桩服务器上测试；2026-10-14 首次对真实 M7 运行 `router pin` 时，普通 `cargo` 构建的预热连接已到达 M7，但内核对它返回空的邻居表，命令因此失败；现须使用 `cargo xtask mooringctl` 签名的副本 `target/signed/mooringctl`（见“构建约定”）。同日稍后 `router pin` 已在本机记录 M7 身份；`router capture --anonymous` 与 `router status` 则在第一个请求即以退出码 8 失败：M7 对不带会话 cookie 的 JSON 请求先以 302 重定向到会话建立地址 `/sess_cd_tmp…`，再重定向回 JSON（实测记录见 M2.md）。客户端现只跟随这一会话建立序列，每次读取 JSON 至多一次、至多三个请求，其他重定向一律拒绝（设计 §15.6 规则 9）。登录被拒时 M7 以 302 跳到 `/index.html?loginfailed&errno=2&errdetail=session.password`，客户端据此直接报告密码被拒；存入正确的管理员密码后，当晚 `router status`（含 `--json`）与两种 `router capture` 均已在真实 M7 上成功运行，两份脱敏抓取经检查不含任何标识，结构与 fixture 一致（见 M2.md）。第 7 版的代码与这次实机运行记录已提交（89d2cdf，2026-10-15）。当时尚未构建引擎、未部署任何 VPS。

## 构建约定

- 工具链固定为 Rust 1.98.1（`rust-toolchain.toml`）。
- 出口 Mac 将作为专用服务器：所有编译输出只写入仓库内的 `target/`，每个里程碑结束执行 `cargo xtask clean`。守护进程运行的是 `cargo xtask install` 安装到 `~/Applications/Mooring.app` 的那一份（该命令 2026-11-10 起提供，出口 Mac 上的守护进程自 2026-11-13 的部署起从这里运行），不在 `target/` 里，所以清理 `target/` 不影响正在服务的守护进程；针对真实部署的命令用已安装 App 内的 `Contents/MacOS/mooringctl`，它与守护进程是同一份构建。从构建目录启动的守护进程（`cargo xtask install` 出现之前都是这样启动的）仍从 `target/app/Mooring.app` 运行，按 `docs/runbooks/console.md` 第 1 节迁移一次之前不要清理 `target/`（`cargo xtask clean` 会拒绝，`cargo clean` 与 `rm -rf target` 不会）。只打开已安装的那一份：macOS 把守护进程和“登录时打开 Mooring”登记在所点击的那份 App 的路径上。xtask 依赖 `mooring-export` 与 `mooring-model`，工作区无法编译时改用 `rm -rf target`（设计 §6.1）。Go 引擎构建与虚拟机测试在研究电脑或托管 CI 上进行（设计 D-7）。
- 交付门槛：`cargo xtask ci` 零错误、零警告。
- `mooringctl` 用 `cargo xtask mooringctl` 构建：它构建该包，把 cargo 报告的可执行文件复制为 `target/signed/` 下的临时文件，以 `com.bill.mooring.mooringctl` 为标识符对这份副本做 ad hoc 签名，要求 `codesign -dv` 报告的正是这个标识符，然后才把它改名为 `target/signed/mooringctl` 并打印该路径。改名之前任何一步失败，`target/signed/mooringctl` 都保持原样，临时文件被删除；若删除失败，则报告 `PartialNotRemoved`（以原失败为其原因）。改名成功后只有最后的提示信息还可能失败。运行被强行中断（Ctrl-C）时可能留下 `target/signed/mooringctl.<pid>.partial`，`cargo xtask clean` 会连同整个目标目录将其删除。只要工作区没有名为 `signed` 的 profile（`[profile.signed]`），cargo 就不写 `target/signed/`，之后的 `cargo build` 或 `cargo xtask ci` 都不会撤销这个签名。签名副本不会随之后的源代码改动更新，因此测量与开发时在工作区根目录、Terminal.app 自己的 shell 里按 `cargo xtask mooringctl && ./target/signed/mooringctl router …` 运行（副本启动时 xtask 已经退出，不是它的祖先进程）：不要经 `cargo run`，中间也不要隔着 ad hoc 签名的 shell 或终端复用器。针对真实部署的命令不用这一份，而用已安装 App 内的 `mooringctl`（见上一条），它是同一种签名副本，同样满足下面的规则。原因（2026-10-14 在 macOS 27.0.1 (26A434) 上实测，规则由实测情形归纳）：内核只向签名标识符为反向 DNS 形式、且不由 ad hoc 签名进程（直接或间接）启动的进程显示邻居表；普通 `cargo build` 的产物由链接器签名为 `mooringctl-<哈希>`，读到的是空表，无法读取 M7 的链路层地址。`macsys` 只如实报告表为空；`mooringctl` 只在已连通网关之后才把空表判断为被内核隐藏：`status`、`capture` 须在匿名 `GET` 成功之后；`router pin` 须预热连接成功，且预热前后两次读取都得到空表（第一次读取不为空，说明本程序能读取该表，此时第二次读到空表报告 `GatewayUnresolved`，退出码 4）。被隐藏时以本地错误（退出码 1）说明原因、提示该命令。它只在 macOS 上运行，不属于 `cargo xtask ci`（`ci` 在各平台执行相同步骤；设计 §15.6 规则 10）。
