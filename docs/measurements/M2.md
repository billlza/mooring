### 3. M7 interface discovery (step 3)

**The web server** identifies as `httpd/2.7 (Netgear; D86)`. `GET /` redirects to `/sess_cd_tmp?op=%2F&oq=` and then to
`/index.html`. The script tags of `index.html` carry the device's IMEI in a `?device=` query string, so Mooring never
requests, logs or stores HTML.

**The endpoint chosen:** `GET /api/model.json?internalapi=1`. `/model.json` was not tried and is never requested
(design §15.6 rule 5).

**Anonymous**, it returns only `session.{userRole, lang, passwordCooloff, secToken, supportedLangList, end}` and
`general.{model, productSKU, InstallID, end}`: not enough for a status, so a login is needed. On 2026-10-13 that answer
was only seen with a session cookie: the one anonymous `GET` of the endpoint was sent after a cookie-less `GET /` had gone
through the `/sess_cd_tmp` redirect, which set one. A cookie-less `GET` of the endpoint was not sent that day; the
inference that the M7 redirects it to `/sess_cd_tmp` as well was confirmed on 2026-10-14 ("The session set-up" below).
`mooringctl` sends its first `GET` without a cookie and follows that set-up, and no other redirect (design §15.6 rule 9).

**The login** is the web UI's form `login_form`: `POST /Forms/config`, `application/x-www-form-urlencoded`, with the
fields, in order, `token` (the anonymous `session.secToken`, 31 characters), `err_redirect=/index.html?loginfailed`,
`ok_redirect=/index.html` and `session.password=<admin password>`. How the M7 answers the `POST` (its redirect target, its
cookies) was not captured on 2026-10-13. On 2026-10-14 it refused a login with a `302` to its login-failed page followed
by `&errno=2&errdetail=session.password`, setting no cookie, and accepted one with a `302` to its start page,
`http://192.168.1.1/index.html`, setting a new `sessionId` cookie ("The login after the set-up" below). A `302` to the
login-failed page is a refused login, named by those two parameters;
otherwise success is decided by the next `GET`, whose `session.userRole` must be `Admin`, and anything else is
`RouterAuthFailed`.

**Authenticated**, it returns about 651 leaves. In plaintext they include `webd.adminPassword`, `wifi.passPhrase`,
`wifi.guest.passPhrase`, `wifi.aux.passPhrase`, the cradle passphrases, `general.IMEI`, `general.InstallID`,
`general.ESN` and `FSN`, `sim.iccid`, `sim.imsi`, `sim.phoneNumber`, the SMS texts and senders (`sms.msgs[]`),
`wwanadv.cellId`, `LAC` and `RAC`, the carriers' physical cell ids and channels (`wwan.lteBandInfo[]`), the GPS position
(`lbs.latitude`, `longitude`), the clients' addresses and names (`router.clientList[]`), the M7's own MACs
(`ethernet.mac`, `wifi.MAC`), the WWAN address (`wwan.IP`), the session token and the client's IP. Only allowlist parsing
is acceptable (design §15.6 rule 1, confirmed).

**The M7's clock** read `general.currTime` 1475954393 (2016-10-08) on 2026-10-13, so no M7 timestamp is trusted: not
`currTime`, `nextBillingDate` or an SMS's `rxTime`. The Mac's poll time is the reading's time. On 2026-10-14 the M7's HTTP
`Date` header matched the Mac's UTC clock to within a second; the rule stands, and `mooringctl` does not read `Date`
either.

#### The session set-up (2026-10-14)

Observed on 2026-10-14 over `en9` (firmware NTGX75_10.04.43.01), after `router capture --anonymous` and `router status`
had both failed at their first request with exit 8, "the M7's answer is malformed: unexpected HTTP status 302". The M7
answers a `GET` of the endpoint without a session cookie with two redirects before the document:

| Hop | Request | Answer and its headers, in order |
|---|---|---|
| 1 | `GET /api/model.json?internalapi=1`, no cookie | `302 Found`: `Server`, `Date`, `Set-Cookie: sessionId=…; path=/; HttpOnly`, `Location` (the set-up target, `/sess_cd_tmp?op=%2Fapi%2Fmodel%2Ejson&oq=internalapi%3D1`, as an absolute URL on `http://192.168.1.1`), `Content-type: text/html`, `Content-Length: 254` |
| 2 | `GET` of the set-up target, with hop 1's cookie | `302 Found`: `Server`, `Date`, `Set-Cookie: sessionId=…; path=/; HttpOnly`, `Location` (the endpoint, `/api/model.json?internalapi=1`, as an absolute URL on `http://192.168.1.1`), `Content-type: text/html`, `Content-Length: 605` |
| 3 | `GET /api/model.json?internalapi=1`, with hop 2's cookie | `200 OK`: `Server`, `Date`, `Cache-Control`, `Content-type: text/plain`, `Accept-Ranges`, `Content-Length: 2159`; the anonymous document |

- The session cookie changes at hop 2: the two values differ (compared by their hashes; neither is recorded).
- Hop 2 is required: the endpoint asked again with hop 1's cookie answers with hop 1's redirect again.
- Each `Location` names the M7 by its address without a port, as the client's `Host` header does, and `op` and `oq` are
  the endpoint's path and query, percent-encoded with upper-case hexadecimal digits (`.` as `%2E`).
- The document is served as `text/plain`, which the client accepts: it refuses only `text/html`.

`mooringctl` now follows exactly this sequence, at most once per read of the endpoint, and refuses every other redirect
as `RouterMalformed` naming the request it answered and its status (design §15.6 rule 9). The login comes after this
set-up (below).

#### The login after the set-up (2026-10-14)

With the set-up followed, `router status` passed the identity check and sent the login, then failed with exit 5: "the
M7 did not grant an administrator's session: the router's session is not an administrator's (the login was answered
with status 302)". So the M7 answered the login with `302`, and the read of the endpoint after it, with the session's
cookies, was not an administrator's. The client kept only that answer's status, so a refused password could not be told
from an accepted login whose session is still not an administrator's.

The M7's web page, fetched anonymously that day, posts exactly the fields the client posts (`token`,
`err_redirect=/index.html?loginfailed`, `ok_redirect=/index.html`, `session.password`), form-urlencoded, with no hashing
in the page. Its script appends `?sessionId=` to the form's action only when the page itself was loaded with a
`sessionId` query parameter, that is when cookies are not in use; `mooringctl` uses cookies.

At that point where the login answer's `Location` pointed was unobserved. In its session set-up the M7 named its own
URLs as absolute URLs on `http://192.168.1.1`, so a login it accepts was expected to be sent to
`http://192.168.1.1/index.html` and one it refuses to `http://192.168.1.1/index.html?loginfailed` *(an expectation, not
an observation)*, and `mooringctl` was made to judge that `Location` byte for byte against exactly those two URLs. Run
again on 2026-10-14, `router status` failed with exit 5 and "the router's session is not an administrator's (the login
was answered with status 302 and a Location elsewhere)".

A one-off diagnostic, kept outside the repository, then repeated `mooringctl`'s requests: the set-up, the anonymous
read, the login (the same fields, form-urlencoded, with the session cookie, and the password the operator typed at a
prompt that does not echo), and one more read. It printed only status codes, each `Location`'s shape (its host, its
path, its parameter names, and the values of the set-up's `op` and `oq` and of `errno` and `errdetail` only),
`Content-Type`, cookie names with short hashes of their values, the session's role and its cool-off; never a cookie's
value, the token, the password or any part of a document.

| Step | The M7's answer (2026-10-14) |
|---|---|
| The anonymous read, after the set-up | `200`; `session.userRole` `Guest`, `passwordCooloff` 0, a token of 31 characters |
| The login `POST` | `302`; `Location: http://192.168.1.1/index.html?loginfailed&errno=2&errdetail=session.password`; `Content-type: text/html`; no `Set-Cookie` |
| The read after it | `200`; `session.userRole` still `Guest`, `passwordCooloff` 0 |

- The M7 sends a refused login to the form's `err_redirect` on its own address followed by `&errno=2&errdetail=` and the
  password field's name. The exact URL `mooringctl` compared with is a prefix of that, which is why it said "elsewhere".
- The refusal sets no cookie, and the session stays `Guest`.
- Four refused logins in a row left `passwordCooloff` at 0.
- The M7's own page script ignores both parameters: it only shows its "login failed" box on `loginfailed`. What the
  M7's error numbers mean is undocumented; reading `errno=2` with `errdetail=session.password` as "the value of the
  password field was refused" is an inference.
- The password the operator had typed was not the M7's admin password. With the right one, the same diagnostic saw
  the login accepted: `302`, `Location: http://192.168.1.1/index.html` (the start page), `Content-type: text/html`, and
  a `Set-Cookie` with a new `sessionId` value; the read after it was `200` with `session.userRole` `Admin` and
  `passwordCooloff` 0. So the session changes at the login too, and the client keeps the new cookie for the read.

`mooringctl` now reads the login answer's `Location` this way (design §15.6 rule 9), keeping no other byte of it:

- the login-failed page is exactly `http://<host>/index.html?loginfailed`, alone or followed by `&` and parameters. Of
  these only `errno` (1 to 4 ASCII digits, read as a number) and `errdetail` are kept, each only when given once; they
  are never decoded, and every other parameter is ignored. `errdetail`, when not empty, is kept only as one of the four
  fields the login form sends (`token`, `err_redirect`, `ok_redirect`, `session.password`, on an exact match), and any
  other value as "another field" with none of its bytes, so nothing a device echoes back there can be printed. The start page, the set-up and the endpoint are still compared exactly;
- a `302` to the login-failed page stops `status` and `capture` at once with exit 5, and nothing more is sent. With the
  parameters observed the error is "it refused the login (error 2 on field session.password, read as the stored admin
  password being wrong); store the password again with `mooringctl router set-password`"; with another field it is,
  for example, "it refused the login (error 7 on field token)", blaming nothing; with nothing given it is the earlier
  "it refused the stored admin password (the login was sent to its login-failed page); store the password again with
  `mooringctl router set-password`";
- any other answer goes on to the read of the endpoint, and when its session is not an administrator's the error names
  the login answer's status and where its `Location` pointed: "(the login was answered with status 302 and a Location
  to the start page)", or to the login-failed page (with what it reported), the session set-up or the endpoint, or "a
  Location elsewhere" (a relative reference, another host, port or scheme, any other URL), or "no Location".

#### The allowlist

`NetgearLeaf` (`crates/daemon-core/src/router/netgear/allowlist.rs`) is the one table both the parser and the
redactor use; a test keeps this copy equal to it. "Read by" names the parse that extracts the leaf: the session parse
reads the anonymous answer's login fields, the status parse everything it needs for `RouterStatus`, never the token.
The redactor keeps every leaf except the secret one. ", or empty" marks the two leaves whose empty string is the M7's
report of no value ("The SMARTY SIM (2026-10-16)" above): the status parse reads it as `None`, the redactor keeps it, and
every other value has the form before the comma. The only other leaf whose shape admits the empty string is
`session.userRole` (`Text 0..=32`): there it is a role, an anonymous session's, which is not an administrator's.

A capture records such a state even when an allowlisted value changes form: a value whose shape the redactor refuses
(an empty or null reading, a number where text belongs, a carrier list that is not an array) is withheld, written as a
placeholder of its type (an empty string stays `""`), and named on the command's output by its path, never its value.
Only a key that is data, a repeated leaf or JSON that is not one object fails the whole capture.
The empty string of `sim.SPN` and of `general.webAppVersion` is not refused: it is the M7's report of no value ("The
allowlist" above), which a capture keeps as `""` without naming it.

**Before the first live run**, both read only towards the M7 and run with the copy that `cargo xtask mooringctl`
builds and signs, `target/signed/mooringctl`, which no later `cargo build` reverts. The copy does not follow later
source changes, so the operator runs each step as `cargo xtask mooringctl && ./target/signed/mooringctl router …` from
the workspace root, in Terminal.app's own shell (xtask has exited by the time the copy starts, so it is not among the
copy's ancestors): never through `cargo run`, and with no ad-hoc-signed shell or terminal multiplexer in between
(design §15.6 rule 10).

1. `mooringctl router pin --interface en9`, answered `y` only if the printed address equals the one recorded locally in
   M2a, otherwise `n` and stop. It prints the gateway's link-layer address from the kernel's neighbour table. When the
   table has no address for the gateway yet (no entry, an incomplete one, or an empty table), it first opens one
   connection to the M7 that sends nothing and reads the table again. If the table still has no address for the
   gateway, the connection's failure, if it failed, is the error. After a successful connection the table is read as
   the kernel hiding it from the binary only when both reads returned it empty: a local error that names
   `cargo xtask mooringctl` (exit 1). A first read that was not empty shows that the binary can read the table, so an
   empty second read is then `GatewayUnresolved` (exit 4), as is an entry still absent. An address the second read
   finds is printed for confirmation even if the connection failed. The placeholder `02:00:00:00:00:00`, which Apple's
   iOS reports in place of a real address, is never pinned (exit 7). Step 2 needs the pin: `capture` reads it before
   it sends anything. The check itself is never weakened: an absent entry, an empty table or the placeholder is never
   a match.
   - 2026-10-13: an ad-hoc-signed test binary, run from a shell started by another application, read an empty table
     (`sysctl` `NET_RT_FLAGS`/`RTF_LLINFO`), and `/usr/sbin/arp -an` run by such a process listed no entry, while the
     same command from the shell listed 11, three of them on `en9`; the default routes stayed visible. This was read as
     local network privacy *(an inference the 2026-10-14 measurement refuted)*.
   - 2026-10-14, macOS 27.0.1 (26A434): `router pin --interface en9`, a plain `cargo` build run from Terminal.app,
     failed with `GatewayUnresolved` while `arp -n 192.168.1.1` in the same Terminal showed the entry on `en9`; its
     warm-up connection to the M7 had succeeded. The kernel returned an empty table to processes whose code-signing
     identifier is not reverse-DNS (cargo signs `mooringctl-<hash>`), and to processes an ad-hoc-signed process had
     started *(that it does so to every such process is an inference from these cases)*: a copy of `arp` signed
     `com.bill.mooring.arpprobe` or `com.bill.mooring.mooringctl` read the entry from the shell, one signed
     `mooringctl` did not, and none did under an ad-hoc-signed parent. The terminal's Local Network setting plays no
     part. Re-signing the build with `codesign --force --sign - --identifier com.bill.mooring.mooringctl` fixed it;
     `cargo xtask mooringctl` now signs a copy of the build that way, at `target/signed/mooringctl`, and checks the
     identifier. The measured cases and the rule are in design §15.6 rule 10.
   - 2026-10-14, later: a `router pin` run failed once with `RouterUnreachable{InterfaceAbsent}` (exit 4) while the USB
     adapter re-attached (the kernel log shows `en9: attached (recycled)` at 19:41:59 local time). A rerun seconds later
     pinned the address, which is kept on this Mac only (design §15.6 rule 4).
2. `mooringctl router capture --interface en9 --out <outside the repo>/anonymous.json --anonymous`. No password is read
